## 2. 技术方案与环境检查

采用 Python + Flask + Jinja 模板 + 原生 CSS/少量 JavaScript + SQLite，提供在本机运行、通过浏览器操作的响应式 Web 应用。

此前建议的 Tkinter 桌面应用不采用：REQ-051 已明确桌面和移动浏览器入口，实验二组件图也使用 WebUI；实验三建议桌面应用不等于必须使用原生桌面 GUI。浏览器方案能保留既有界面设计并支持多用户请求验证。

| 项目 | 2026-11-03 本机检查结果 | 实施安排 |
|---|---|---|
| 操作系统 | macOS 26.6.2，arm64 | 作为首个运行与演示环境 |
| Python | `python3` 为 3.13.3 | 以 Python 3.13 为首个验证版本 |
| SQLite | Python 模块报告 3.53.3 | 使用标准库 sqlite3；启用外键、事务、WAL 和有限等待 |
| Tkinter | 导入失败，缺少 `_tkinter` | Web 方案无需安装 |
| Flask / pytest / Ruff | 当前 Python 环境中均未发现 | 实施阶段创建虚拟环境并安装，验证后锁定具体版本 |
| Git | `/usr/bin/git` 可用；已有本地仓库及 origin | 使用现有仓库，不重新初始化 |
| 远程仓库 | `https://github.com/235826/secondhand-marketplace.git` | 尚未检查远程访问权限或执行推送 |
| 报告工具 | 检测到 Pandoc、XeLaTeX 可执行文件 | 报告阶段验证中文 PDF 渲染，当前未转换报告 |

依赖预计包括 Flask、Flask-WTF（表单及 CSRF）、Pillow（图片解码验证）、pytest、Ruff。安装时确认兼容性并固定版本；本步骤不安装。口令采用标准库提供的带随机盐 scrypt，使用参数化 SQL、服务端授权和输出转义。

应用分为表现层、应用服务层、领域层、仓储与基础设施层。路由只解析请求和组织响应，业务权限、状态判断及事务边界由应用服务统一维护。领域模型不依赖 Flask 或 SQLite。

本地开发默认仅监听回环地址。REQ-052 的 HTTPS 纳入 HTTPS 配置和验收任务；单独运行 HTTP 开发服务器不算通过该项。实验提供本地 TLS 或反向代理配置，报告区分本地证书演示与可信证书部署。

## 4. 实验约定与设计差异

| 事项 | 依据/问题 | 采用的实现约定 |
|---|---|---|
| Web 界面 | REQ-051、组件图已经使用浏览器 | 响应式服务端模板，参考实验二 12 张界面；无需前端构建工具 |
| 数据库 | 组件图标注 MySQL | 实验改用 SQLite 便于复现；使用仓储接口隔离差异；性能是否满足以实测为准 |
| 管理员创建 | REQ-004 写“已有管理员”，用例图和实验二报告限定初始管理员 | 采用更具体的实验二规则：只有 INITIAL_ADMIN 可创建管理员，普通 ADMIN 拒绝 |
| 管理员模型 | 类图使用继承 | 领域层保留 User/Admin/InitialAdmin 的语义及权限区别；数据库统一 users 表，用 role 区分，注册接口不得接受自选角色 |
| 学校邮箱 | 需求未给出完整域名清单 | 支持域名用配置明确列出；演示默认 `nju.edu.cn`、`smail.nju.edu.cn`，按完整域名匹配；这是实验配置，非学校域名权威清单 |
| 邮箱服务 | REQ-002/010/052 需要验证，当前无邮件服务配置 | 定义 EmailService，开发模式在专用本地 outbox 展示测试邮件；验证码仅保存摘要、限时、限次、单次使用并区分用途；不进入审计日志。真实发送由 SMTP 适配器接入，未配置时不得声称已验证邮箱真实归属 |
| 预约与成交确认 | 类图时间字段不足以区分卖家确认预约和确认成交 | 分设 seller_accepted_at、seller_trade_confirmed_at、buyer_trade_confirmed_at；预约状态与成交确认独立 |
| 改价与旧确认 | UML 缺少新价接受及确认版本 | 保存 accepted_version_id/accepted_price、confirmation_version_id；任何新送审版本清空原成交确认，新价通过后要求买家独立接受；未改价时旧价格接受可沿用，但双方仍须对当前审核版本重新确认成交 |
| 重审通过 | 状态图只画待审→已发布 | 有有效锁定则恢复 RESERVED，否则 PUBLISHED；驳回保持隐藏和原锁定，取消锁定不能把待审/驳回商品改成已发布 |
| 草稿与待审编辑 | REQ-012 允许撤回或重新提交 | 待审编辑采用重新提交新不可变版本，旧审核请求失效；重复提交同一请求不增加待审版本 |
| 删除和违规 | 八种商品状态没有 DELETED | 使用 deleted_at 逻辑删除，与八种状态分开；违规处置终止活动预约候补，删除不破坏历史；已成交商品处置只限制展示，不改变 SOLD 或成交事实 |
| 下架公开性 | REQ-035 允许历史公开下架商品查询 | OFFLINE 且曾审核发布、未删除且无违规限制时可看不可约；待审、驳回、违规内容不公开；由历史审核版本提供安全展示 |
| 未登录申诉 | Appeal 类仅关联 Complaint，无法表示直接冻结账户的申诉 | 增加 ModerationAction，记录处罚对象、原因和处理人；Appeal 关联处罚，可选关联投诉；未登录核验令牌仅能提交/查询本人申诉，不能取得普通业务会话 |
| 交易沟通 | REQ-053，现有 UML 未建留言类 | 增加 ReservationMessage，按预约关联限制双方访问，界面只显示昵称；公开及卖家预约响应不输出买家邮箱/手机号 |
| 冻结有效期 | REQ-009 要求起止时间 | 存储冻结起止时间，认证及每次受保护操作检查有效期；到期恢复及管理员解除留痕，旧会话受处罚后立即失效 |
| 统计口径 | REQ-036 区分当前商品和历史成交 | 商品数取未删除、已审核且处于公开历史状态的商品；成交数取不可变成交记录，使用成交分类快照，不受后续商品删除影响 |

上述约定可用于开始实现；若后续用户调整，更新本文及受影响验收项。实验二原文件本步骤不修改，实验三将提供与实现一致的 UML 副本和差异说明。

## 6. 状态与事务规则

1. 新商品从 DRAFT 开始；送审信息须包含名称、描述、分类、合法价格、成色、至少一张合规图片、交易地点和备注。草稿允许暂不完整。待审新版本不得公开。
2. 正式预约仅允许活跃用户预约他人 PUBLISHED 商品，并校验页面版本。事务内创建 LOCKED 预约并更新商品为 RESERVED。数据库部分唯一索引保证每商品最多一个 LOCKED/SELLER_CONFIRMED 预约。
3. 同一用户不能同时拥有同一商品的有效预约与 WAITING 候补；两表交叉约束在同一写事务内检查。失败抢约不自动建立候补，买家需主动选择。
4. 卖家确认预约后变为 SELLER_CONFIRMED，但不代表确认成交。候补按加入时间和 ID 排序，只能由卖家在无活动锁定时确认最早有效候补；失效账户可跳过并记录原因，不自动转正。转正按卖家已确认预约处理。
5. 成交前任一交易方可取消；卖家可拒绝。取消清除成交确认并释放锁定，仅在商品仍可售时恢复 PUBLISHED。重审或驳回期间取消不恢复公开展示，不设置自动预约超时。
6. 已发布或已预约商品修改送审后为 PENDING_REVIEW，保留有效预约并暂停确认成交。审核通过后按锁定情况恢复 PUBLISHED/RESERVED；驳回继续隐藏。价格接受及确认版本按第 4 节执行。
7. 成交要求预约已被卖家接受、双方账号仍有效、商品通过当前审核、买家已接受当前价格、双方确认属于同一有效版本。第二个有效确认在单事务内写成交记录、预约 COMPLETED、商品 SOLD、其余候补 TERMINATED。
8. 重复成交确认返回已有结果，不重复记账；取消与最终确认竞争由事务生效顺序决定。SOLD 不允许取消、重新上架或恢复预约资格。
9. 下架、删除、违规封禁同步终止未成交预约和候补、清除确认。违规解除只移除限制，不直接发布；重新送审通过后才能恢复。所有未列入合法集合的转换拒绝。
10. 写事务使用独立连接、明确事务边界和有限锁等待；预约、转正、取消、重审和成交按当前状态条件更新，不依赖进程内锁。唯一约束冲突转为业务拒绝；忙等待耗尽不能伪装为预约成功。
11. 成功业务与成功审计在同一事务提交。业务校验拒绝或事务回滚后，用独立事务记录拒绝日志；若日志写入也失败，返回可识别的系统错误，不伪造审计成功。查询日志不得泄露凭据。
12. 所有权限在服务层检查；冻结和封禁不仅限制登录，还限制已有会话继续操作。表单使用 CSRF，图片校验格式/大小/内容并使用受控路径，SQL 参数化，日志及页面输出脱敏。
